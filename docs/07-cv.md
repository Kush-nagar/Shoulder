# 07 — Deferred computer vision

## Purpose

Computer vision may reduce the time a coach spends searching a match. It does not decide whether a player acted well, identify a development need, or write feedback. Its only product output is an `observation`: a time range and neutral machine metadata that a coach may inspect, assign, or reject. Deletion follows the referenced/unreferenced rules below rather than an unrestricted delete action.

The manual product in Tasks 1–22 must work across three real matches before this work begins.

## Product boundary

```text
CV artifact -> candidate rule -> observation -> coach inspection -> human judgment
```

The boundary is intentionally one-way:

- A model cannot insert or publish a `judgment`.
- A candidate cannot appear in the player product.
- A player cannot see track IDs, probabilities, detection failures, or rejected candidates.
- A coach cannot convert a candidate into player-facing evidence without watching it and writing the sentence.
- The live application remains fully usable if every CV job is disabled or deleted.

## Phase gate

Start Phase D only after all of the following are recorded in `STATUS.md`:

The complete mandatory real-use gate in `docs/06-tasks.md` also applies, including review-time, player-open, reflection, and repeat-use criteria. The checks below add CV-specific readiness evidence; they do not replace or weaken that gate.

1. Three complete real-match uploads and transcodes succeeded.
2. At least one coach completed the manual mark, classify, write, and publish loop in each match.
3. Draft marks survived one intentional network interruption and reload.
4. Player isolation and clip-object tests passed.
5. The measured manual review time and the reason CV is needed are written down.

If the manual product is not useful, do not use CV to hide that problem.

## Research workspace boundary

SoccerMaster, weights, extracted frames, and third-party datasets stay in a separate private research workspace. The Shoulder repository contains only:

- input preparation that emits a documented job bundle;
- an adapter contract for invoking an external runner;
- an ingest validator for immutable artifacts;
- deterministic candidate rules;
- evaluation scripts using consented Shoulder footage or synthetic fixtures.

As of 2026-08-24, the inspected SoccerMaster repository had no license file. Do not copy, vendor, redistribute, publish, or deploy its source or weights from the Shoulder repository. Recheck the upstream repository, model cards, and dataset terms before Task 24 and again before any public demonstration.

## Offline pipeline

1. A coach or operator selects a completed video segment.
2. The local preparation command reads source metadata with `ffprobe` and creates a manifest.
3. The operator explicitly starts an encrypted GPU workspace.
4. Only the selected video and manifest are transferred.
5. The external runner writes its declared raw artifacts and an environment manifest.
6. Results are copied back, checksummed, and validated before ingest.
7. The GPU workspace and temporary input/output storage are destroyed after checksum verification. A separate encrypted network volume may retain only licensed reusable weights under an explicit retention policy; no team frames/media/artifacts persist there.
8. Shoulder ingests one immutable `cv_run`, its tracklets, and neutral observations.
9. A coach manually associates useful tracklets with a player for that run.
10. Deterministic rules nominate moments for inspection.

No GPU service is reachable from a public HTTP route. No live request waits on inference.

## Input manifest

Each job bundle has a versioned `manifest.json` containing:

| Field | Contract |
|---|---|
| `schema_version` | Exact adapter schema, initially `1` |
| `run_id` | UUID allocated before transfer |
| `video_id` | Shoulder video UUID |
| `segment_start_ms` / `segment_end_ms` | Bounds in original-video time |
| `source_sha256` | Exact selected input bytes |
| `source_width` / `source_height` | Decoded display dimensions |
| `source_fps_num` / `source_fps_den` | Rational frame rate; do not round |
| `rotation` | Normalized display rotation |
| `created_at` | UTC timestamp |
| `requested_outputs` | Explicit artifact names and versions |

Reject inputs with unsupported codecs, corrupt timestamps, ambiguous rotation, or a checksum mismatch. Record the rejection without leaking local paths.

## Immutable artifact contract

The runner must produce:

```text
run.json
detections.json.gz
tracks.parquet
environment.json
checksums.sha256
```

`run.json` records model/version identifiers, command arguments, timebase, start/end bounds, processing duration, status, and artifact schema versions. `environment.json` records OS, CUDA, Python, framework, package-lock hash, and GPU model. It contains no credentials.

Each detection or track sample uses original-video `timestamp_ms`; frame numbers are secondary diagnostic fields. Track IDs are scoped to one run and never treated as stable player identities.

Minimum track columns:

- `run_id`, `track_id`, `timestamp_ms`;
- normalized `x`, `y`, `width`, `height` in `[0,1]`;
- detector class and raw confidence;
- optional ball coordinates and visibility;
- optional team-color cluster local to the run;
- source artifact row identifier.

Do not store face crops, appearance vectors, face embeddings, voiceprints, gait templates, or any persistent biometric identifier.

## Ingest rules

- Validate every artifact against a versioned schema before any database write.
- Verify all checksums and the source hash.
- Insert a run and its track index in one transaction.
- Treat `(run_id, track_id)` as the track identity.
- Store per-frame output in Parquet/JSON objects, not Postgres.
- Store only run summaries, tracklet bounds, coach assignments, and candidate observations in Postgres.
- Re-ingesting an identical artifact is idempotent.
- A changed artifact creates a new run; it never mutates a completed run.
- Run deletion removes raw artifacts, tracklets, assignments, and only observations with no judgment reference. It does not cascade through a referenced observation or alter a human judgment/revision.

### Phase D deletion exception

This contract is implemented in Task 27 only, after the gate; it does not add pre-gate CV schema or dependencies. See [ADR 0011](decisions/0011-cv-provenance-deletion.md).

- Keep `judgment.observation_id` non-null with `ON DELETE RESTRICT`. A referenced observation retains its ID, video/player, source label, and original-video time range. Human judgment revisions and player publication snapshots remain unchanged.
- For a referenced CV observation, a restricted cleanup transaction sets `cv_provenance_status='removed'`, clears `cv_run_id`, any removed segment provenance, confidence, event/features, and artifact pointers, then deletes the run/track data. No CV metadata is copied into revision history to evade cleanup.
- Add `cv_provenance_status` in Phase D, constrained to `present`/`removed` for CV candidates and null for non-CV observations. `present` requires a run; `removed` requires cleared machine fields. This explicitly replaces the earlier unconditional run-required rule for retained CV candidates. Do not relabel system candidates as coach-authored manual observations.
- Unreferenced CV observations may be deleted during run cleanup. Serialize this with judgment creation so a concurrent human judgment either keeps its observation or fails safely before referencing a deleted row. Repeat cleanup is idempotent.
- This narrow provenance-erasure exception does not permit ordinary edits to append-only observations. Full player/season erasure can remove the dependent graph in FK-safe order under `docs/10-security-privacy.md`.
- Test both referenced and unreferenced candidates, concurrent creation, repeated deletion, intact human revisions, and absence of residual machine fields and artifact objects.

## Candidate rules

Rules are small, deterministic functions over artifact data. They must have a name, semantic version, declared inputs, parameters, output reason code, and unit tests.

Allowed initial categories include:

- player enters a configured zone;
- player is within a configured distance of the ball;
- possession-change window near an assigned tracklet;
- off-ball run lasting a minimum duration;
- tracklet continuity break that warrants manual inspection.

These are retrieval hints, not assessments. Name reason codes neutrally—for example `entered_zone_v1`, not `poor_positioning`.

Candidate output contains only:

- `video_id`, `cv_run_id`, `track_id`;
- start and end time in milliseconds;
- rule name/version and parameter snapshot;
- neutral reason code;
- provenance pointer into the immutable artifact.

It contains no score visible in the product. Raw model confidence may remain in restricted research artifacts but is not an ordering signal in the UI.

## Evaluation protocol

Create a frozen, consented evaluation set with manually marked reference windows. Split by match, never by nearby frame, so adjacent moments cannot leak between evaluation and development sets.

Measure:

| Measure | Meaning | Initial go/no-go signal |
|---|---|---|
| Window recall | Reference moments with at least one candidate overlap | Report by match; prefer recall over precision |
| Candidate burden | Candidates shown per 90 minutes | Must fit the coach's review time budget |
| Keep rate | Candidates a coach converts to a draft judgment | Must beat random/time-grid sampling |
| Tracklet purity | One real player per assigned tracklet | Report median and worst-match failures |
| Time saved | Manual review time minus assisted review time | Positive across at least two matches |
| Reproducibility | Same frozen input produces same normalized candidates | Exact match after allowed float normalization |

Do not select a model from aggregate accuracy alone. A useful system must save coach time without creating misleading certainty.

## Cost and privacy controls

- The operator sees the exact clip duration and estimated GPU spend before starting.
- Each run has a hard wall-time and spend cap.
- Use the smallest useful segment before a full-match run.
- Disable public network ingress on the GPU workspace.
- Store temporary inputs and outputs on encrypted volumes.
- Transfer with short-lived credentials scoped to one prefix.
- Destroy the pod and temporary volume after checksum verification, including on failure.
- Never use team footage to train or fine-tune a third-party model without a separate consent and legal review.

## Failure behavior

CV failure is quiet in the player experience. Coaches may see a plain operational state—queued, running, completed, failed, or canceled—with a retry action and diagnostic reference. A failed run cannot block uploading, manual review, publishing, playback, or reflection.

## Future ranking boundary

No learned candidate-ranking work begins until the repository contains at least 2,000 coach-authored keep/reject outcomes, the privacy review is repeated, and a new ADR explains the benefit. Even then, ranking may order neutral candidate observations for a coach; it may not rank players, goals, or performance.
