# 05 — Screen behavior

The coach experience assumes a laptop and frequent keyboard use. The player experience assumes a phone, one thumb, intermittent 4G, and a short session. `docs/09-frontend-design-system.md` defines the visual system; this file defines what each screen does.

## Route map

```text
/login

/coach
/coach/roster
/coach/players/[player_id]
/coach/upload
/coach/games/[game_id]
/coach/games/[game_id]/review/[player_id]

/player
/player/goals/[goal_id]
/player/progress
```

The app redirects from `/` only after a verified session and role lookup. Do not infer role from route or client state.

## Login

One email field, one primary action, one paragraph explaining that a sign-in link will arrive. A submitted state replaces the form with “Check your email” and a safe resend timer. Responses do not reveal whether an account exists.

No testimonial carousel, feature list, animated background, or marketing hero. This is a private team tool.

## Coach shell

Desktop navigation contains Dashboard, Players, and account. “Upload match” is the persistent primary action on ordinary coach pages. The current team and season appear once in the shell, not on every card. The high-focus review route uses a distraction-free shell with only Back to match, save state, and keyboard help.

At widths below 1024px, ordinary coach pages collapse to a compact rail or top navigation. The review page displays a clear “Best on a laptop” message below 768px but still allows view-only playback and draft comments; keyboard-speed acceptance is tested at desktop widths.

## `/coach` — Dashboard

Answer one question: what needs attention?

Order:

1. Games whose video is processing or ready for review
2. Reviews with unpublished drafts
3. Recent player reflections

Each row has one next action. Do not show KPI cards, team totals, averages, charts, percentages, or “engagement.”

Empty state: “Upload your first game” with one button and one sentence about what happens next.

## `/coach/roster`

Default is a compact table: player, number, position, active goal, account state, next action. Search is local and appears only above ten rows.

First-use empty state is a bulk paste area accepting `name, number, position`. Parse into a preview table, show row-level errors, and require confirmation before an all-or-nothing save.

Adding one player uses an inline row or small dialog. Archive is separated from edit and requires confirmation. Invitations are secondary; the coach can use the entire workflow before collecting player email.

## `/coach/players/[player_id]`

Top section: player identity and exactly one active goal. If none exists, the primary action is “Set a goal.”

Below:

- Evidence timeline grouped by game
- Optional reflections in chronological order
- Closed goals in a collapsed section

Evidence uses one dot per published judgment: filled for applied, outlined for opportunity. It has no connecting trend line, axis pretending to measure ability, score, or percentage.

## `/coach/upload`

Sequence:

1. Select a game or enter game details.
2. Drop/select one video.
3. Validate extension, size, and browser-readable metadata.
4. Upload parts with overall and current-part progress.
5. Confirm storage completion.
6. Show processing state and explain that the coach may leave only after upload completion.

Copy while uploading: “Keep this tab open while the file uploads. If the connection drops, you can resume the missing parts.”

Copy after completion: “Upload complete. It is safe to close this tab while Shoulder prepares the video.”

On reopen, show the matched file name/size/modified time and ask the user to reselect the same file if browser permissions did not persist. Never restart completed parts.

## `/coach/games/[game_id]`

Shows opponent/date, video processing state, and one review row per active player. States: not started, draft count, exporting clips, published, failed action required.

The processing component uses plain stages: Uploaded, Preparing video, Creating timeline, Ready. Progress is approximate; do not animate a false percentage when the worker cannot measure it.

## `/coach/games/[game_id]/review/[player_id]`

This is the product's critical screen. A coach must create three to six judgments for one player in under three minutes without touching the mouse.

### Desktop layout

- Top context bar: player, number, active goal, save state, keyboard help.
- Main left column: 16:9 video, transport controls, thumbnail timeline, observation markers.
- Right review rail: current timestamp/duration, verdict controls, comment, clip count, candidate list, publish action.
- At 1024–1199px the right rail is 320px; at 1200px+ it is 360–400px. Video owns remaining width.
- The page itself does not vertically scroll during active review; the candidate list scrolls inside its region.

### Keyboard map

| Key | Action |
|---|---|
| Space | Play/pause unless editing text |
| J / K / L | Rewind / pause / forward; repeated L increases playback rate |
| Left / Right | Seek −1 / +1 second |
| Shift + Left / Right | Seek −10 / +10 seconds |
| I / O | Set clip in / out |
| 1 | Applied |
| 2 | Opportunity |
| 3 | Not relevant |
| C | Focus coach comment |
| Enter | Save current draft and advance when valid |
| Escape | Return focus to video controls |
| ? | Open keyboard help |

Shortcuts do not fire while the user types except Escape and the explicit save shortcut. Every shortcut has a visible/button equivalent and an accessible name.

### Review behavior

- Creating in/out points immediately stores a local draft and optimistically writes to the API.
- Save status is quiet text: Saving, Saved, Offline — saved on this device, or Needs attention.
- Candidate markers show source to coaches only: manual or CV candidate. Confidence is not shown by default.
- Verdict 3 keeps the observation and judgment as `not_relevant` but removes it from the publish count.
- Publish stays disabled until 3–6 valid, non-rejected judgments exist.
- Publish opens a compact verification surface listing clip count and player; it does not show a celebratory confirmation.
- When publish starts, the coach may leave; the game page shows export progress.

### Failure behavior

- Reload restores every local draft, clip boundary, comment, and verdict.
- A stale-server conflict preserves both versions and asks the coach to choose; it never overwrites silently.
- An expired playback URL refreshes without resetting current time.
- A worker failure leaves all draft data intact and offers one retry action.

## `/player` — Mobile home

Show:

1. “Working on” and the active goal
2. Latest published game with clip count and date
3. Earlier games, if any

No dashboard cards for empty categories. If no goal exists: “Your coach hasn't set a goal yet.” If a goal exists but has no evidence: “Your coach will add clips after a game.”

## `/player/goals/[goal_id]`

The page opens at the newest game and clip 1.

For each clip:

1. Player-safe verdict label
2. Coach's sentence
3. Isolated video clip
4. Optional “What did you notice?” field
5. Previous/next controls and “Clip 2 of 4”

The coach's sentence comes before video so the player knows what to look for. Do not autoplay. Preserve playback position during short URL refreshes. Preload metadata only for the next clip, not all video bytes.

Reflection supports save and skip. “Skip” is neutral and equally available. After save: “Reflection saved.” The player may edit or remove it later.

## `/player/progress`

Show the active goal and evidence grouped by game. Filled and outlined dots match the coach view, with a text legend. A player may open a dot to revisit that clip. Do not show totals in a way that encourages comparison; “4 clips from Saturday” is fine, “19 total clips” is unnecessary.

## Notifications

Email only.

| Event | Recipient | Timing |
|---|---|---|
| Video prepared | Coach | Immediate |
| Processing failed | Coach | Immediate with one recovery action |
| Evidence set ready | Player | Once after all clips publish |
| Reflection submitted | Coach | Daily digest |

The dashboard may show the reflection in ordinary recent activity without creating a separate notification. No reminder that a player has not watched. No push, SMS, in-app notification center, streak, or read receipt exposed to the coach.

## Global states

**Loading:** reserve final geometry; use skeletons only for content that is actually pending. Never show a full-screen spinner for ordinary navigation.

**Empty:** explain why and offer one next action.

**Error:** state what happened, what was preserved, and the next action. Provider names and codes stay out of player copy.

**Offline:** preserve coach drafts locally; player pages explain that the clip needs a connection and keep reflection text until it can save.

**Forbidden/not found:** use the same not-found surface for resources hidden by authorization.

## Player-facing prohibitions

- No full-match controls or URLs
- No other player's name, number, clip, or goal
- No CV source, confidence, boxes, tracks, or model language
- No “good/bad player” colors
- No ratings, trend arrows, grades, percentages, ranks, team averages, or comparisons
- No shame copy, urgency, countdowns, reminders, or engagement mechanics
- No analytics or third-party scripts on player routes
